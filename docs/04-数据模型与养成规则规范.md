# 数据模型与养成规则规范（双端单一事实源）

- 文档版本：v1.0
- 适用范围：Android（Kotlin）与 iOS（Swift）镜像实现；`GrowthEngine` / `DialogueEngine` / `ReminderPlanner` 必须按本文档伪代码逐行对齐
- 配套数据文件：`shared/schema/pet_db_schema.sql`、`shared/assets/*.json`
- 镜像测试约定：见 `tests/README.md`

---

## 1. 通用约定

1. **时间单位**：一律为 Unix 毫秒时间戳（Kotlin `Long` / Swift `Int64`）。
2. **命名**：数据库列与 JSON 导出字段一律 **snake_case**（如 `last_active_at`）；双端代码内部字段用各自语言惯例（camelCase），但映射必须逐列对照 §2。
3. **禁止硬编码**养成数值常量：所有规则常量唯一来源为 `shared/assets/growth_rules.json`，镜像单测以 JSON 为准（单测内允许内联同等数值以构造用例，但需标注来源）。
4. **状态读取约定**：任何读取宠物状态的入口必须先过 `lazilyApplyDecay(now)`；`lastActiveAt` 在任何用户互动（点按/喂食/聊天）后刷新。
5. **与类图的偏离说明**：类图中 `hunger/mood/intimacy` 标为 `Int`，实现采用 **`Double`（DB 列 REAL）** 存储——惰性衰减按流逝时间连续结算，整数存储会造成逐次舍入漂移、破坏双端一致性；对外展示（UI/通知/快照摘要）时四舍五入为 `Int`。

## 3. 养成规则（GrowthEngine 伪代码，双端逐行对齐）

```
clamp(v) = min(valueMax=100.0, max(valueMin=0.0, v))

// —— 惰性衰减：任何读取状态前调用；不修改 lastActiveAt ——
applyElapsedDecay(state, lastActiveAt, now, rules):
    hours = max(0, now - lastActiveAt) / 3_600_000.0
    state.hunger   = clamp(state.hunger   + rules.hungerDecayPerHour   * hours)
    state.mood     = clamp(state.mood     + rules.moodDecayPerHour     * hours)
    state.intimacy = clamp(state.intimacy + rules.intimacyDecayPerHour * hours)
    return state

// —— 喂食：先衰减后增益（PetRepository.feed 内部顺序：decay → feed → levelUp）——
applyFeed(state, food, rules):
    state.hunger   = clamp(state.hunger   + food.hungerGain)
    state.mood     = clamp(state.mood     + food.moodGain)
    state.intimacy = clamp(state.intimacy + food.intimacyGain)
    state.exp     += food.expGain
    return state

// —— 升级：可连升多级；满级后经验封顶不再累计 ——
expToNextLevel(level) = levelBase(100) + (level - 1) * levelStep(50)

checkLevelUp(state, rules):
    while state.level < rules.maxLevel(99) and state.exp >= expToNextLevel(state.level):
        state.exp -= expToNextLevel(state.level)
        state.level += 1
    if state.level >= rules.maxLevel(99):
        state.exp = min(state.exp, expToNextLevel(rules.maxLevel) - 1)
    return state
```

规则常量（growth_rules.json，代码不得硬编码）：

| 常量 | 初始值 |
|---|---|
| hungerDecayPerHour | -2.0 / 小时 |
| moodDecayPerHour | -1.5 / 小时 |
| intimacyDecayPerHour | -0.5 / 小时 |
| levelBase / levelStep | 100 / 50（即 `expToNextLevel(L) = 100 + (L-1)*50`） |
| maxLevel | 99 |
| valueMin / valueMax | 0.0 / 100.0 |
| hungerLowThreshold / moodLowThreshold | 30 / 30（UI 低状态警示用） |
| tapMoodGain / tapIntimacyGain | 1 / 1（点按互动增益） |

## 4. 对话匹配算法（DialogueEngine 伪代码）

语料文件 `shared/assets/dialogue_zh.json`，格式：

```
rules[]:      { id, keywords[], priority, responses[] }
fallback[]:   未命中时随机一句
tapReactions[]: 点按互动随机台词
feedReactions: { full, normal }  喂食反馈（normal 中 {food} 替换为食物名）
```

匹配算法（双端一致）：

```
normalize(input) = trim(input).lowercase()        // 仅 ASCII 转小写，中文原样
respond(input):
    if normalize(input) 为空:  从 tapReactions 随机取一句返回
    hits = []
    for rule in rules:
        exact = rule.keywords 中存在 kw 使 normalize(input) == normalize(kw)
        partial = rule.keywords 中存在 kw 使 normalize(input).contains(normalize(kw))
        if exact or partial: hits.add((rule, exact))
    if hits 非空:
        按 priority 降序排序；同 priority 内 exact 优先于 partial；稳定性排序
        取排序后第一条 rule → 从其 responses 随机取一句
    else:
        从 fallback 随机取一句
    返回 DialogueResult(text, ruleId 或 "fallback")
pickTapReaction(): 从 tapReactions 随机取一句
```

**随机数约定**：选择语料用注入的伪随机数生成器（`Random.nextInt(size)` / `Int.random(in:)`），默认随机种子由系统提供；镜像单测注入固定种子保证两端同一序列。

## 5. 提醒计划算法（ReminderPlanner 伪代码）

```
nextTriggerTime(config, from):                    // config: ReminderConfig
    if not config.enabled: return 0               // 0 = 无效（未启用）
    intervalMs = config.intervalMinutes * 60_000
    base = config.nextTriggerAt ?: (from + intervalMs)   // 从未排程：从现在起一个周期
    next = base
    while next <= from: next += intervalMs               // 已过期：顺延到未来第一个整周期
    return next                                          // 未来：保持原排程时间
```

- Android：到点触发后由 Receiver 以返回值重排下一次 Alarm（AlarmManager 精确 + WorkManager 周期兜底）。
- iOS：UNUserNotificationCenter 重复触发（`UNTimeIntervalNotificationTrigger(repeating: true)`），`nextTriggerAt` 仅作展示/对齐。

## 9. 灵动岛喂食快捷按钮协议：App Group `pending_actions.json`（QA 第 1 轮补记）

**背景**：灵动岛扩展进程（PetLiveActivity target）无法访问主 App 的 SwiftData/文件存储（不同沙盒），喂食快捷按钮（FeedAppIntent）采用「写待处理动作文件 → 主 App 前台消费」的两段式协议：

1. **写入方（PetLiveActivity 扩展，`PetLiveActivityUI.swift` 的 `FeedAppIntent.perform()`）**：
   - 向 App Group 根目录写 `pending_actions.json`，原子写入（.atomic）：
     ```json
     { "type": "feed", "food_id": "dried_fish", "created_at": 1769900000000 }
     ```
   - `type` 固定 `"feed"`；`food_id` 当前固定 `"dried_fish"`（小鱼干）；`created_at` 为 Unix 毫秒时间戳；
   - 写入后调用 `WidgetCenter.reloadAllTimelines()` 并通过 `openAppWhenRun = true` 拉起主 App。
2. **消费方（主 App，`Views/RootView.swift` 的 `consumePendingActions()`，`.task` 首帧触发）**：
   - 读取并校验 `type == "feed"` → **立即删除文件（防重复喂食）** → `repository.feed(food_id)` → `refreshSystemSurfaces()`（PNG 导出 → 灵动岛更新 → 小组件重载）。
3. **约定**：
   - 扩展进程只写、主 App 只读+删，双方互不等待（无锁，靠「读后即删」保证幂等）；
   - 文件名与字段名双端硬编码一致（本节为唯一事实源）；后续扩展其他快捷动作（如摸头）时新增 `type` 取值，消费方按 type 分发；
   - 该协议为临时方案：若后续主 App 持久化迁移到 App Group 共享存储，可改为扩展进程直接写库，本协议作废。
